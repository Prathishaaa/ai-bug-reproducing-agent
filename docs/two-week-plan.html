Build the AI Bug Reproducing Agent in 14 days

You give it a GitHub bug report. It guesses the cause, writes a test, and runs the test in Docker until the same error appears. Then it saves the proof.

> python agent.py your-name/bug-samples 2 attempt 1 guess: bad input type test passed try again attempt 2 guess: empty cart not handled FAILED test_bug.py::test_empty_cart - ZeroDivisionError SAME ERROR AS THE BUG on attempt 2 of 4 Saved to results/2.json

The idea in one minute

Before anyone can fix a bug, someone must make it happen on purpose. That is called reproducing it, and it often takes hours. Your agent does this first job. It does not fix the bug.

ReadDownload the code and the bug report
ThinkGemini guesses the cause and writes a test
RunDocker runs the test in a sealed box
JudgePython checks if the error matches the bug
No match? The output goes back to Gemini for a new guess, up to 4 attempts. This loop makes it an agent. A single AI call would only be a chatbot answer.

Day2

Make your practice bugs

New GitHub repo: bug-samples

  2. Hide 3 bugs in it: an empty cart causes ZeroDivisionError, a missing item causes KeyError, text as a price causes TypeError.

Build the parts

Talk to Gemini

Day4

Get the code and the bug report

download.py

  1. Run git clone from Python with subprocess, into a workspace/ folder. Add that folder to .gitignore.
  2. Fetch the issue with requests from api.github.com/repos/OWNER/REPO/issues/NUMBER.
  3. Save the title and body to a text file.
Day5

Read the bug, pick the files

prompts.py, pick_files.py

  1. Write your first prompt. Ask Gemini to return only JSON with error_type, keywords and file_names.
  2. Search all .py files for those words and rank files by number of matches.
  3. Keep the top 3 files. This saves your free requests and helps Gemini focus.
Day6

Build the sealed box

Dockerfile, docker_run.py

  1. Write a 4-line Dockerfile: start from python:3.12-slim, install pytest, build it as bug-box.
  2. Write a test by hand first. No AI today.
  3. Run it from Python with subprocess.run and capture the output. Mount only the cloned project, never your whole laptop.
docker run --rm --network none --memory 512m -v "PROJECT_FOLDER:/app" -w /app bug-box timeout 60 pytest test_bug.py
Day7

Build the judge

check.py, test_check.py

This is the most important file in the project. A failing test proves nothing unless it fails for the right reason. Count a match only when all 3 rules are true:

  1. pytest shows a FAILED line, which means the test ran. A broken test shows ERROR instead.
  2. That line names the same error as the bug report.
  3. The traceback passes through a project file. This catches a test that simply runs raise ZeroDivisionError.

Make it an agent

Join the parts. By the end of day 10, it reproduces your sample bugs from one command.

Day8

One full attempt

agent.py, prompts.py

  1. Add a second prompt. Give Gemini the bug and the picked files, and ask for JSON with guess and test_code.
  2. Write test_code to test_bug.py in the cloned project.
  3. In agent.py, call the parts in order: download, read, pick, guess, run, judge.
Day9

Add the loop

agent.py, prompts.py

  1. Wrap the attempt in for attempt in range(4). Stop as soon as the judge says match.
  2. Send each earlier guess and its output to Gemini with the words "this did not work, try a different cause".
  3. If Gemini returns bad JSON, count it as a failed attempt. Do not crash.
Day10

Save results and handle errors

save.py, agent.py

  1. Save every guess, test, output and final status to results/NUMBER.json.
  2. Show clear messages when Docker is off, the repo is missing, or the Gemini limit is reached. On a limit error, wait and retry once.
  3. Accept the repo and issue number from the command line.

Prove it

Your own bugs are easy. Real bugs give you an honest number, and that number is what makes this project stand out.

Day11

Try real bugs

bugs.csv, Dockerfile

  2. Note the commit just before each fix, so the bug is still in the code. Add git checkout to download.py.

Day12

Get your number

evaluate.py, results/summary.csv

  1. Loop over bugs.csv. Skip any bug that already has a result, so a stopped run can continue tomorrow.
  2. Record for each bug: reproduced or not, attempts used, and time taken.
  3. Find 2 numbers: bugs reproduced on attempt 1, and bugs reproduced in any attempt. The difference shows what your loop adds.

Know these before you start

Free Gemini limits are small

Forum users report about 20 requests a day on newer Flash models and about 500 on Flash-Lite. Check your real limits in AI Studio. One bug uses 2 to 5 requests, so start on Flash-Lite and spread real-bug runs across days 11 to 13.

Keep the scope small

This agent handles Python bugs that raise an error. It will not handle UI bugs, timing bugs, or wrong results with no error. Saying this clearly in your README and interview shows good judgement.

Expect a modest score

Many real bugs will not reproduce, and that is normal. A real "4 of 10" that you can explain is far stronger than a claim you cannot defend. Your 3 sample bugs do not count in this number.

Be careful with code and data

Docker lowers the risk from AI-written code, but does not remove it. On the free tier, Google may use what you send to improve its products. Send only public code, never company code.

What interviewers will ask

Why a loop and not one AI call? The first guess is often wrong. The real output gives Gemini new evidence, and your attempt 1 vs final score shows how much this helps.

How do you know the bug is really reproduced? Python decides, not the AI. The test must run, fail with the reported error, and fail inside project code.

How do you keep AI-written code safe? It runs in Docker with no internet, a memory limit, a 60-second limit and access to only one folder.

Why not send the whole project to Gemini? It costs requests and tokens and adds noise. A simple keyword search sends only the likely files.

What would you improve next? Point to your failed bugs in summary.csv and name the most common reason they failed. Your own data makes this answer strong.
